# 補足説明なしで読める資料をつくる

## 対象と到達目標

読者はSE・PM経験があり、個々のニュースの専門用語は知らない人。会議中の口頭説明を前提とせず、後日PDFだけを開いて内容を理解する。

従来サンプルでは根拠の文章を入力に残していても、その多くがスピーカーノートに置かれ、紙面は短い図ラベル中心だった。入力の充実と、読者に見える説明の充実は別である。この改善では `explanation` を意味モデルに加え、図と同じ紙面に説明を出す。

## 入力契約

```json
{
  "explanation": {
    "readerQuestion": "このページを読んで何が分かるか？",
    "sections": [
      { "heading": "前提と用語", "body": "読者が知らない用語や業務背景を説明する。" },
      { "heading": "図から読み取ること", "body": "要素の関係と、なぜこの結論になるのかをつなぐ。" },
      { "heading": "判断の限界", "body": "評価条件、未確認事項、出典事実と提案の境界を示す。" }
    ]
  }
}
```

セクションは1〜3個。見出しは固定語ではなく、説明したい内容に合わせる。説明はノートだけへ退避せず、生成したスライド本文に表示する。情報が収まらない場合は意味単位でページを分ける。文字を自動縮小したり、文を切り捨てたりして成功と扱わない。

六種類の関係は本文の意味を表す。説明を増やすために矢印を消す、並列を工程に変える、または無関係な循環を追加しない。複雑な関係を一枚に詰めず、共通の問いでまとまる範囲に分ける。

## 執筆と検証の順序

1. 読者・用途と、読み終えた時に答えられるべき問いを決める。
2. 背景 → 用語 → 課題 → 仕組み → 根拠と条件 → 限界 → 次の判断の順序を検討する。すべてを毎ページに重複させない。
3. ボディの対象範囲・分解軸と関係を定め、`content` に保持する。
4. 図だけでは推測が必要な説明を `explanation` に書く。事実と執筆者の提案を分ける。
5. 出典URL・発表日・条件を可視の紙面にも置く。リンクやノートを開かなければ主張の意味が分からない状態を避ける。
6. 機械テスト・描画検査を行う。全ページの画像、最終PDF、編集可能PPTXを確認する。
7. 元記事・ノート・口頭説明なしの読者役が問いに答える。答えられない項目は入力と生成処理へ戻して修正する。

## 合否は文字数で決めない

- 何の話か、誰のどんな困りごとか説明できるか。
- 初出の専門用語を紙面だけで理解できるか。
- 図の矢印・集合・並列の意味と、結論までのつながりを説明できるか。
- 数字の母数・測定主体・比較条件・計算上の仮定が分かるか。
- 検証結果、将来目標、執筆者の解釈を区別できるか。
- 不明点と次の確認事項が分かるか。
- 小さすぎる文字、切れ、重なりがなく、一枚ずつ読む順序が自然か。

機械検査の通過は意味上のMECEや理解可能性の認証ではない。独立したアシスタントの評価はユーザー承認と記録しない。PPTXは表示環境によって変わるため、検証したビューアーと未検証の環境を明記する。

## 再現例

`npm run example:explanatory` はNECの同じ発表を8ページに再構成する。発表の規模を水増しせず、読者の疑問ごとに説明を分ける。`examples/research/nec-explained-2026-10-15.json` が原本で、書き出したPPTXを後から手修正した例ではない。

```sh
npm run check
npm run example:explanatory
npm run preview -- examples/research/generated/nec-explained-2026-10-15.pptx .preview/explanatory
```

制約：自由文からの自動MECE保証、任意の長文の自動ページ分割、複合関係の自動選択は対象外。まず、著者が作った説明を失わず描画し、読者評価から改善できることを検証する。

## 図の対象と説明の対応

説明セクションの任意の `nodeRefs` で、同じスライドの明示的な `content` ノードIDを参照する。
未定義ID、同じセクション内の重複IDは入力検証で拒否する。参照は作者が意味を確認して付けるもので、文章から自動推定しない。

参照がある場合は表現層がノードに `[1]` 等の照合番号を付け、説明見出しにも同じ番号と同じ要素名を表示する。
番号はスライド内の照合キーであり、並列図に順序や因果を追加しない。ノードIDは元入力で維持される。
`nodeRefs` がないセクションは「全体」と明示し、個別対象の説明と区別する。
色だけに対応を依存せず、文字を読めば対象を特定できるようにする。

複数の `nodeRefs` は複数対象への説明を表す。エッジの参照や因果関係を意味しない。
エッジ固有の説明・矢印ラベル・説明行とノードの厳密な縦位置整列は今回未対応。
六関係の構造と既存矢印は保持する。必要情報が収まらないときは意味のまとまりでページを分ける。

再現例: `examples/research/github-security-linked-2026-10-16.json`。
元の8ページの対象を保ち、適格性と費用、長いDocs URLを別ページにして10ページにした。
元の出典・制約・費用・未実測事項は保ち、文字を小さくして押し込まない。
図と説明の対応は改善対象であり、機械検査だけで説明の正しさや理解しやすさを認定しない。
